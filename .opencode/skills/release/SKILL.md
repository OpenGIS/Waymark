# Waymark Release Skill

Releases are single-source and CI-driven: edit the version in `Waymark.php`, run the tests, and push. CI syncs the derived files, builds the assets, deploys to WordPress.org and creates the GitHub Release.

## Version bump

The plugin version is single-sourced from the `Waymark.php` header — the only manual version edit:

| File            | What to change                        |
| --------------- | ------------------------------------- |
| `Waymark.php:7` | `Version: X.Y.Z` in the plugin header |

Everything else is derived and handled by CI (`grunt sync_version build`):

- `readme.txt` `Stable tag` and `package.json` version — synced from the header by `sync_version`
- `readme.md` and `languages/waymark.pot` — regenerated by the build
- `assets/css/*` and `assets/js/*` — rebuilt from the LESS and JS sources

Never edit the derived files by hand.

## Pre-release checks

Run the test suite and confirm the results are as expected:

```bash
npm test
```

> [!NOTE]
> `npm test` is the pre-release gate — run it and confirm the full suite is green; no release ships with any test failing.

## Release workflow

1. **Agree the version** with the maintainer (e.g. `1.6.9`).
2. **Edit `Waymark.php:7`** — update the `Version:` line. This is the only manual edit.
3. **Run the tests** — `npm test` (the full pre-release gate: Vitest, PHPUnit and Playwright).
4. **Summarise** — list the changed files for the maintainer to review, stage and commit.
5. **Push to `master`** — CI takes over (see below).

## What CI does on push

`.github/workflows/ci.yml` detects the version change and:

- syncs `readme.txt` / `package.json` versions (`grunt sync_version`)
- rebuilds CSS, JS, `languages/waymark.pot` and `readme.md` (`grunt build`)
- deploys to WordPress.org SVN (including `.wordpress-org/` assets)
- creates a GitHub Release tagged `vX.Y.Z`
- commits the synced artefacts back to `master` (`chore: sync release artefacts for vX.Y.Z`)

No manual deploy step beyond the push. If the version did not change, the workflow exits without deploying.

## Manual recovery

The sync + build are idempotent and available locally:

```bash
npx grunt sync_version build
```

If CI fails before the deploy step, run the command above, inspect the result, then re-run the workflow from the GitHub Actions tab. For local development, use `npm run grunt` for a one-shot build or `npm run grunt:watch` to rebuild on change — do not run bare `grunt` (the default task ends with a blocking watch).

## Local distributable

`npm run dist` builds a CI-faithful plugin zip at `.opencode/tmp/waymark-<version>.zip`.

It copies tracked files into a temporary tree, runs `grunt sync_version build`, applies `.distignore`, and zips the `waymark/` folder. The repository is not modified; use the zip to inspect or test-install the distributable.

## Changelog

No per-version changelog entry is written — `== Changelog ==` in `readme.txt` only links to the GitHub commit history.

## WordPress.org assets

`.wordpress-org/` mirrors the WordPress.org SVN `assets/` directory (banners, icons, screenshots, and the README hero image). The deploy workflow syncs it to SVN with `rsync --delete`.

The readme screenshots are generated from the tested demo data. Recapture them with `npm run screenshots` (writes `editor-demo.jpg` and `screenshot-1..9.jpg` into `.wordpress-org/`), verify the captures with `npm run screenshots:check`, and include any updated assets in the release.

> [!WARNING]
> Every asset that should stay live must be present in `.wordpress-org/` — the deploy deletes anything missing. Maintain the full set, not just changed files.

Asset and readme changes only reach WordPress.org on the next **version bump** (the deploy workflow fires only when the pushed commit changes `Version:` in `Waymark.php`). The 10up `action-wordpress-plugin-asset-update` action could push readme/asset updates between releases — not currently configured.
